## 1. Field `id` on transaction create

**GitBook** (`editor.md`) **sends a client UUID** in the body example:

```json
{
  "paymentMethod": 2,
  "id": "3fa85f64-5717-4562-b3fc-2c963f66aza6",
  "paymentDetails": { "amount": 970, "currency": "RUB" },
  "description": "test",
  "return": "https://google.com",
  "failedUrl": "https://yourdomain/fail",
  "payload": "1111"
}
```

(in the GitBook source, commas after `return` and `failedUrl` are missing.)

**docs.platega.io:** "Transaction ID is generated by the system automatically — do not pass field `id` in the request." Schema `CreateTransactionRequest` has no `id` field.

Treat the GitBook example as **stale**. Do not send `id` on the current API.

### Error "Transaction already exists"

GitBook 400:

```json
{
  "statusCode": 400,
  "message": "Transaction 3fa85f64-5717-4562-b3fc-2c963f66afa6 already exists."
}
```

"A transaction with this id already exists in the system. To fix this, change the transaction id and send the request again."

Only makes sense in a model where the client sets `id`. On the current API, if it arrives — a sign the client is still sending its own UUID.

## 2. GitBook payment methods

GitBook table "List of available payment methods":

| Name | Value |
| --- | --- |
| SBP / QR | `2` — NSPK / QR |
| CardRu | `10` — Card 2dcs, MIR card payments |
| International | `12` — International acquiring |

Prose on the same page: body shape for QR/SBP and P2P is the same, only `paymentMethod` differs. "For QR / SBP we always send number 2. All other methods, including method 1, 2–9, are related to P2P methods."

GitBook totals:

| int | GitBook |
| --- | --- |
| `1`–`9` | P2P (while `2` is also named SBP/QR) |
| `10` | CardRu / 2dcs MIR |
| `12` | International |

Current `PaymentMethodInt`: `2, 3, 11, 12, 13, 14`. No `1`, `4`–`10`. `3` ERIP, `11` card acquiring, `13` crypto, `14` Sberpay are absent from the GitBook table. `6` subscriptions are not in GitBook.

Do not put `10` / P2P `1`–`9` into new code until the manager / current docs confirm it.

## 3. GitBook statuses

GitBook "Check status" (`images-and-media.md`):

| Status | GitBook description |
| --- | --- |
| `PENDING` | waiting for payment |
| `CONFIRMED` | payment confirmed |
| `EXPIRED` | payment expired |
| `CANCELED` | cancelled payment |
| `FAILED` | payment create error |

Current `PaymentStatus`: `PENDING`, `CANCELED`, `CONFIRMED`, `CHARGEBACKED`.
`EXPIRED` and `FAILED` are **not** in the official schema. `CHARGEBACKED` is **not** in the GitBook list.

Status response fields in GitBook match the current ones, including typos `mechantId`, `comission`, `comissionUsdt`, `comissionType`.

## 4. H2H — different JSON

**docs.platega.io:** `{ "amount": 136.12, "qr": "https://qr.nspk.ru/..." }`

**GitBook** (`markdown.md`): first create a transaction, then `GET app.platega.io/h2h/{id}` with the transaction id.

```json
{
  "accountNumber": "2200 7004 0146 3121",
  "maskedAccountNumber": "2200 7004 0146 3121",
  "accountName": "Jhon M",
  "method": "tinkoff",
  "amount": 2000
}
```

(in the GitBook source the comma after `"tinkoff"` is missing.)

Fields `accountNumber` / `maskedAccountNumber` / `accountName` / `method` are not in the current H2H OpenAPI. For a new integration — `{amount, qr}`. If a live response looks like GitBook — document the fact, do not break the parser on a single variant.

H2H in both sources requires manager enablement (current docs).

## 7. GitBook callback

- URL in cabinet Settings → Callback URLs — matches.
- Headers `X-MerchantId` + `X-Secret` — matches.
- Body camelCase: `id`, `amount`, `currency`, `status`, `paymentMethod` — matches the current payment callback.
- Success `CONFIRMED`, failure `CANCELED`. **No** `CHARGEBACKED` in GitBook prose.
- Timeout 60 s, 3 retries × 5 minutes — matches.
- No HTTPS/CA/private-IP requirements (those exist only in current docs).
- No subscription PascalCase callbacks.

Fake callback: create a tx **in the cabinet**, press the button, pick a fake status. GitBook: CONFIRMED / CANCELED.
